# Cloudflare OPC Agent 入门实战

把 [opc-ops](https://github.com/liangdabiao/opc-ops-skill) 这个「一人接私活防坑 SOP」skill
完整移植成一个有状态 Agent：**金额与风险判断由确定性工具完成，模型只负责判断与话术**。

- ✅ **25 条风险规则**（红线 / 需留意 / 正向）扫描客户沟通记录 → 直接给「接 / 不接 / 条件接」
- ✅ **金额计算**：分期拆分 / 中途叫停结算 / 维护报价（整数分运算，误差为零）
- ✅ **8 份模板**：合同大纲 / 报价单 / 需求文档 / 周报 / 中期确认单 / 验收清单 / 结项报告 / 维护合同
- ✅ **B1~B11 全流程 + A0/A2 经营层**：按阶段渐进式注入知识
- ✅ **项目工作台**（skill 原本没有的能力）：多项目建档、阶段推进、定金进度
- ✅ **自动建档**：说「客户李四，电商小程序，合同3万」自动落库

## 为什么这个案例特别

前六个案例展示的是「怎么把 Agent 搭起来」，这个案例展示的是 **怎么把一套人类 SOP 变成 Agent**。

关键认知：**SOP 里大部分内容不是规则，是判断**。
「客户说整体还行，但那个啥你再改改」——这是验收问题？变更问题？还是他在找借口压价？
关键词匹配不出来（实测这两类句子命中 0 条规则）。所以：

| 层 | 谁来干 | 理由 |
|---|---|---|
| **算术**（分期 / 结算 / 维护报价） | 确定性工具 | LLM 会把 ¥8,000 算错，且错得自信 |
| **模板拼装**（占位符替换、缺项检测） | 确定性工具 | 这是字符串操作，不是判断 |
| **阶段判断 / 风险结论 / 该说什么话** | **模型** | 真实场景是模糊的、多义的；规则化会给出"正确但没用"的答案 |
| **该看哪份资料** | **模型**（调 `read_reference`） | 关键词只能给候选线索，不该剥夺模型的选择权 |

换句话说：**规则是脚手架，不是牢笼**。我最初把 19 条关键词做成硬路由、只注入单一阶段知识、
强制四段式输出，结果模型在真实模糊输入上被绑住手脚——这一版已改回"模型主导判断"。

## 架构

```
用户输入
   ↓
[候选线索]（关键词只提供"可能相关的阶段"，不是路由指令）
   ↓
[自动建档]（确定性抽取：客户名 + 金额，仅创建草稿档案）
   ↓
注入：核心理念 + 候选阶段动作 + 起步知识（≤7000 字）
   ↓
LLM 自主判断：这是哪个阶段？跨阶段吗？该不该反问？该取哪份资料？
   ↓
┌────────── 确定性工具（0 Neurons）──────────┐
│ calc_deal         分期 / 结算 / 维护报价     │
│ render_doc        模板占位符填充 + 缺项清单  │
│ scan_client_risk  25 条规则 → *初步信号*     │
│ read_reference    按需取 4 份手册全文        │
│ save_project      项目档案                  │
└─────────────────────────────────────────────┘
   ↓
模型自己的表达：结论 → 该做哪几步 → 要不要产出物 → 最该防的那条风险
（接单/交付类问题通常这个顺序更清楚，但**不强制套模板**）
```

## skill → Agent 映射表

| opc-ops 组件 | Agent 实现 | LLM 成本 |
|---|---|---|
| SKILL.md 五原则 + 路由表 | 精简系统提示 + 候选阶段线索 | 低 |
| `references/` ×4（38KB） | 起步注入 1 份 + 模型按需调 `read_reference` 取其余 | 低 |
| `assets/` ×8（26KB） | `render_doc` 模板引擎 + 前端下载 | **0** |
| `scripts/risk_scan.py` | `src/lib/risk-scan.ts`（25 条规则原样保留，结论降级为"初步信号"） | **0** |
| `scripts/deal_calc.py` | `src/lib/deal-calc.ts`（Decimal → 整数分） | **0** |
| 无（skill 是无状态的） | 项目工作台（DO SQLite） | 0 |

## 实测记录（Free 计划）

| 场景 | 输入 | 结果 |
|---|---|---|
| 客户风险 | 「你先做着，做完了我们再谈钱」 | ✅ 命中红线 → 婉拒 + 话术 |
| 分期计算 | 「1万6，定金多少、怎么分期」 | ✅ ¥8,000 / ¥4,800 / ¥3,200（与 Python 一致） |
| 混合信号 | 「李四，电商小程序，3万，月底上线」 | ✅ 自动建档 + 0 红线 3 正向 → 「可继续推进，缺可量化目标」 |
| 模板生成 | 「要交付了，生成验收清单」 | ✅ 生成 .md + 列出待填占位符 + 一键下载 |
| **模糊场景** | 「整体还行，但那个啥你再改改；做了两个月，尾款还没给」 | ✅ 模型自判"这句话有点危险"，列三种可能（真拖着不付 / 拿验收当借口 / 把验收当改改台阶），调 `calc_deal` 出维护报价，反问关键信息 |

## 核心概念速查

| 概念 | 说明 |
|---|---|
| 确定性 vs 判断的分界 | 算术与字符串操作交给工具；语义理解、结论、话术交给模型 |
| 候选线索 ≠ 路由指令 | 关键词只告诉模型"可能相关的几个方向"，最终判断权在模型 |
| 渐进式加载（模型驱动） | 起步只注入 1 份资料，不够用由模型调 `read_reference` 自己取 |
| 工具结论的可质疑性 | `scan_client_risk` 输出的是"初步信号"，提示词允许模型说明理由后**不同意**它 |
| `@callable` | 前端直接调服务端方法（工作台读写项目），不必经过对话 |
| 自动建档 | 服务端正则抽取「客户名 + 金额」，只创建草稿档案（不抢判断权） |
| 整数分运算 | 金额一律用「分」的整数表示，避免浮点误差 |
| 不强制输出格式 | 给"通常更清楚的顺序"作为建议，模糊场景优先把话说到点子上 |

## 已知限制

- **模板是通用行业示例**：`acceptance-checklist` 等模板内含设备管理系统的示例行，
  模型会提示与你的项目不匹配——这是刻意保留的（模板是结构参考，不是成品）
- **关键词线索会漏**：模糊表述常命中 0 条规则（这正是设计允许的——此时模型自己判断，
  不依赖规则）；只有需要单一阶段编号的地方（如工作台默认值）才用 `routeStage`
- **合同/条款不构成法律意见**：正式签约前请律师复阅（skill 原文的免责声明同样适用）
- **Workers AI 每日 10,000 Neurons**：本案例确定性工具不耗额度，但对话本身仍计费
